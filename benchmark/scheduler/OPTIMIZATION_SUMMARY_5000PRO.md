# RTX PRO 5000：历史冷缓存调度优化汇总

> 当前发布基于社区 v0.5.17 的 29481685，只包含 sjtushenhai 的优化提交；
> 同事的 14 个内部基础提交及其改动已移除。下文性能、配置和源码哈希是
> 之前组合环境的历史记录，不能据此宣称当前社区基线分支已达到 51%～52%。
> 当前提交与验证范围见 [社区基线发布说明](OPTIMIZATION_COMMITS_20261010.md)。


本文记录早期 auto_qps、P95 E2E ≤5000 ms 的调度试验。当前用例版本
`202609111724`、平均 E2E ≤1500 ms 的 NVFP4／FA4 优化及继续摸高结果，见
[容量优化汇总](CAPACITY_OPTIMIZATION_5000PRO.md)。两轮负载和 SLA 不同，
QPS 不能直接横向比较。

该阶段已验证版本为 cold-v4：在每轮清空 KV cache、P95 E2E ≤5000 ms、成功率 ≥99%
的条件下，实测达标请求速率由原始 **2.2 QPS 提高到 2.6 QPS（+18.2%）**。
其中，同参数仅开关自研 PD 调度的独立增益为 **2.5 → 2.6 QPS（+4%）**。
18.2% 包含并发参数调整，不能全部归因于 PD 代码。3 QPS 尚未达标。

cold-v5 已完成：3 / 2.7 QPS 的 P95 为 5947 / 5075 ms，未通过；2.6 QPS
两轮为 4863 / 4502 ms，仍只达到 2.6 QPS，未证明额外收益，已恢复 cold-v4。
running24 对照因用户接手启动服务而中止，未形成推荐结论。

## 验收口径

单卡 RTX PRO 5000 72GB Blackwell，模型 chatrl-glm-flash-0625-fp8。运行用户的
HTTP auto_qps，CHAT 数据集、200 请求、2 repeats、非流式、temperature=0.6、
top_p=1、输出上限 128。每个 repeat 前验证队列为空并成功调用 flush_cache；
保留原 runner 的 1 条 warmup，以及首轮失败便停止下一轮的行为。

所有比较保持输入、抽样和对应轮的到达种子、模型和六个内核环境变量一致。
不启用确定性推理，因此输出长度有采样波动，逐轮保存输出总量。清缓存后，
本轮请求间仍自然复用前缀，实测输入 token 命中率约 22%；没有使用上一轮缓存。

## 实测结果

| 配置 | 达标 QPS | 两轮 P95 E2E | 更高速率的失败证据 |
| --- | ---: | --- | --- |
| 原始 commit b1478c429，FCFS/16K/running6 | 2.2 | 4851 / 3719 ms | 2.3：5227 ms；3：7180 ms |
| 并发调至 running16，PD 关闭 | 2.5 | 4927 / 4424 ms | 2.6 两次重启首轮：5177 / 5099 ms |
| running16，cold-v4 PD 开启 | 2.6 | 4992 / 4460 ms | 2.7：5073 ms；3：5804 ms |
| running16，cold-v4 PD 开启，重新启动仅测 2.6 | 2.6 | 4709 / 4483 ms | 两轮均通过 |

原始基线从独立、干净的 b1478c429 worktree 启动，核对了导入位置、原启动参数及
内核环境。独立 PD 对照使用相同六份运行源码和参数，只切换 pd_slo_ms=0/5000。
关闭 PD 的第二次 2.6 QPS 复核输出 17525 token，低于开启后的两个首轮
18399 / 17812 token，仍未达标，因此收益不只是输出更短造成的。
上述为有限样本、0.1 QPS 附近的实测边界，不是容量置信区间或所有流量的保证。

## 怎么优化

1. 将最大运行请求数从 6 提至 16，减少运行槽位等待，让更多 decode 请求同批推进。
   保留 FCFS、16K prefill 预算、固定 interval=0。这属于参数收益。
2. 新增 SLO 驱动的 P/D 分时调度：根据请求已耗时、预计剩余输出和 GPU 实测耗时，
   为 decode 分配时间；prefill 执行后积累 decode 时间额度，实际 decode 执行后扣除。
   再用有限的完成时间预测决定是否值得额外等待，避免无条件 prefill 打断生成。
3. 保留 API 接入时间，包含分词和服务端排队；CUDA event 异步学习实际 P/D 耗时；
   按已生成长度估计剩余输出，预测请求完成后 batch 缩小。连续推迟 prefill 的
   上限在调度点检查，为 min(500 ms, SLO × 10%)，不会抢占已提交的 forward。

## 为什么 PD 增益有限

这是同一张 GPU 上的 P/D 分时，P 和 D 仍消耗同一份 GPU 时间。fresh cold-v4 对照中，
观测到 prefill 53.59 秒、decode 94.13 秒，prefill 占这两者总和约 36%。时间片不能
消除未命中的输入计算，也不能减少用户要求的生成量。旧策略还可能连续推迟 prefill，
使新请求等待过长；限制这种额外等待的 cold-v5 并未提高已测达标 QPS。

2.6 QPS fresh 对照的首轮，PD 关闭时 14/200 个请求超过 5 秒，开启时 1/200；
最慢 10 个请求平均生成约 128 token。现有收益集中在尾延迟，而非显著降低计算总量。
