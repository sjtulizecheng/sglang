数据如何经过 Attention

K32 为什么比 K16 快

两者都使用 FP8 输入、FP32 累加。K 表示单条 Tensor Core MMA 指令的求和维度，与量化位宽、KV cache 的 K 无关。

计算相同 16×8 输出块，求和长度 64K16K32
所需 MMA 指令数42
单条指令处理的求和元素数1632

历史版本的 QK 已经是 K32；PV 升级为 K32，同时调整 V 的字节转置、16 字节对齐和 P 的寄存器打包。它减少指令发射和累加依赖的开销；单条指令的硬件成本可能不同，加载、softmax 和量化仍占时间。

历史实测：准备+Attention 耗时约降低 14%；同并发 8，QPS 从 5.78 到 6.05（+4.67%）。这是 K32 与配套布局的组合收益，不是端到端速度翻倍。

Decode 候选：KV 分块并行与归约

逻辑依赖示意，无时间比例。每个请求生成一个 token；沿缓存序列拆分任务，每个任务内部依次执行 Q 量化、QK、在线 softmax 和 PV。

候选配置：batch 1～2 用 64 splits；3～4、8～11 用 32 splits；其余用 16。每个分块的长度按 64 个 KV token 对齐，短序列可能出现空分块。分块越多，并行度越高，但也会增加重复 Q 量化、部分结果写入和归约工作；收益随 batch 与序列长度变化。

分块数改变在线 softmax 的归约次序及 P 的 FP8 量化分组，结果可能发生变化，不能视为逐位一致的调度调整。新内核必须在 CUDA Graph 捕获前安装；已在 batch 1～16 的捕获内部记录到指定分块数。旧晚安装的 7.52 QPS 不能评价此候选，实际质量与吞吐结果见下方。

本轮新增优化：Router 与投影

上面的 FP8 Attention 内核沿用上一轮版本。本轮目前的主要增益来自将其他耗时算子放到合适的 Tensor Core 路径，并调整 prefill 与 decode 的执行间隔。

如何判断优化有效

先比较同一真实输入的准备+Attention 总耗时，再检查变长输入、前缀、空因果行及图重放。候选通过后进行相同条件的 HTTP 压测和复测。

达标目标同时要求吞吐至少 7.686 QPS、平均 E2E ≤1500 ms，并核对成功率和输出长度。算子提速不能代替服务结论。
